# 2026-05-27 工作记录

## 系统调度优化 - chunk_loader_system 拆分

**目标**：提升 FPS，减少系统间锁竞争。

**变更**：
- 将 `chunk_manager::chunk_loader_system`（9 个 ResMut 参数的单一系统）拆分为 5 个独立系统
- `chunk_manager.rs` 新增 5 个 `pub fn`：
  1. `collect_and_upload_meshes` — GPU 网格上传（First 调度）
  2. `process_pending_deletions` — 分帧删除区块实体（First 调度）
  3. `manage_chunk_load_state` — 玩家移动检测 + 加载队列 + 卸载 + LOD + LRU（Update 调度）
  4. `spawn_entities_from_prepare` — 准备结果 → 实体创建 → 提交 Generate 任务（Update 调度）
  5. `submit_prepare_tasks` — 提交 Prepare 任务到工作线程（Update 调度）
- `main.rs` 系统调度重构：
  - First: collect_and_upload_meshes → process_pending_deletions（链式）
  - Update 前部: manage_chunk_load_state → spawn_entities_from_prepare → submit_prepare_tasks
  - 后接原有 camera/input/raycast/hud 系统

**设计要点**：
- frame_counter 仅由 collect_and_upload_meshes 递增一次，后续系统通过 `loaded.frame_counter` 读取
- spawn_entities_from_prepare 使用 `loaded.last_player_chunk`（由上一系统设置）
- 旧 chunk_loader_system 保留为死代码（main.rs 不再调用）

## 查询优化 - run_if 条件跳过空操作帧

**目标**：减少空闲帧中不必要的 ResMut 锁和 CPU 消耗。

**变更**：
- `chunk_manager.rs` 新增 3 个 `run_if` 条件函数（行 750-776）：
  1. `has_pending_deletions(Res<LoadedChunks>)` — 检查待删除队列
  2. `has_load_queue_items(Res<LoadedChunks>)` — 检查加载队列
  3. `has_pending_prepare_results(Res<AsyncMeshManager>)` — 检查工作线程待处理任务
- `main.rs` 更新 3 个系统的注册：
  - `process_pending_deletions` → `.run_if(has_pending_deletions)`
  - `spawn_entities_from_prepare` → `.run_if(has_pending_prepare_results)`
  - `submit_prepare_tasks` → `.run_if(has_load_queue_items)`

**效果**：
- 空闲帧（玩家静止）：3 个系统完全跳过，不获取 ResMut 锁，不消耗 CPU
- 活跃帧：行为与原一致，无性能回退
- 条件函数使用 `Res<T>`（只读），系统使用 `ResMut<T>`，Bevy 调度器自动串行化

## 避免展开 ChunkData — 删除 to_shared_vec + 标记 to_vec

**目标**：消除 32KB ChunkData 展开为 Vec<BlockId> 的性能风险。

**变更**：
- `chunk.rs` 删除 `to_shared_vec()`（行 413-419）：零调用者，纯死代码
- `chunk.rs` 给 `to_vec()` 添加 `#[deprecated]`（行 413-414）：
  唯一调用者 `gpu_meshing.rs:232` 所在文件未被任何模块引用（废弃的 Indirect Draw 路径）

**分析**：
- `to_shared_vec()` → Arc<Vec<BlockId>> — O 次调用，每次调用分配 32KB 堆内存
- `to_vec()` → Vec<BlockId> — 唯一调用者在 `gpu_meshing.rs`（未导入的废弃模块）
- 两个接口均非活跃代码路径，`get(x,y,z)` + `ChunkData` 直接访问是正确替代方案

## 修复纯空气区块放置方块不渲染

**问题**：向纯空气区块（未创建 Mesh 实体）放置方块后，方块不渲染仅高亮。

**根因（两处关联 bug）**：

1. **`block_interaction.rs` `place_block` else 分支**（行 226-268）：
   - 使用 `Handle::default()` 作为占位 Mesh/Material 句柄 → 无效！
   - 缺少 `Mesh3d`、`MeshMaterial3d`、`ChunkAtlasHandle` 组件
   - 对比：`spawn_entities_from_prepare` 使用 `shared_empty_mesh.handle` 且包含所有必需组件

2. **`chunk_manager.rs` `collect_and_upload_meshes`**（行 822-842）：
   - 当 `old_handle` 为 `Handle::default()` 且 `meshes.get_mut` 返回 `None` 时，代码静默失败：不创建新 Mesh 也不报错，导致实体拿到无效的 `Mesh3d`

**修复**：

- `block_interaction.rs`：
  - 导入 `ChunkAtlasHandle`, `AtlasTextureHandle`, `SharedEmptyMesh`, `SharedVoxelMaterial`
  - `block_interaction_system`/`place_block` 增加 `shared_empty_mesh`, `shared_material`, `atlas_handle` 参数
  - else 分支使用 `shared_empty_mesh.handle` / `shared_material.handle` 替代 `Handle::default()`
  - 实体 spawn 补全 `Mesh3d`, `MeshMaterial3d`, `ChunkAtlasHandle` 组件

- `chunk_manager.rs`：
  - `collect_and_upload_meshes` 安全网：`meshes.get_mut(&old_handle)` 返回 `None` 时创建新 Mesh（而非静默失败）

**修复后数据流**：
  place_block → 共享空Mesh占位 → rebuild_dirty_chunks → 异步网格生成 → collect_and_upload_meshes → old_handle==shared_empty_mesh → 创建新Mesh → Mesh3d(新Handle) → 渲染正确
