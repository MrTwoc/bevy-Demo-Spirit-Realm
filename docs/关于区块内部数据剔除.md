关于Voxy模组区块管理方案

**区块保留（Retention）：**
- 玩家周围一定范围（比如 4-8 区块）的完整区块会完全保留，正常渲染
- 超出这个范围的区块不会被卸载，而是被 **转换成低精度的 LoD 网格**保存下来，继续显示但细节减少
- 走远之后原始区块数据会被释放，只保留 LoD 数据

**剔除（Culling）：**
- **视锥体裁剪**：
摄像机背后的区块直接不渲染
- **距离分级剔除**：距离越远，LoD 等级越低，到最远阈值直接不显示（类似雾效但更可控）
- **遮挡剔除**：被地形/建筑完全挡住的区块也跳过渲染

所以它不是简单粗暴的"远距离直接不渲染"，而是一个 **渐进式降级 + 分层次剔除** 的机制，
这也是它能上几千区块视距还不掉帧的原因。

如果远处的原始区块数据被释放，那保留的LOD数据具体包含了哪些信息？

Voxy 的 LOD 数据本质上是把原版区块 **体素化（voxelize）** 后的简化信息，大致包含这些：

**① 简化的方块类型**
不是完整的 Minecraft BlockState，而是粗粒度的分类——草方块、石头、水、空气、树叶等等。
每个体素只需要少量字节就能表示"这是什么"，不需要记录完整的属性（比如朝向、水位高度这类细节全丢了）。

**② 颜色信息**
每个体素带有对应方块的**平均颜色值**（从材质贴图采样）。这是 LoD 渲染的核心——远处看到的地形色彩就是靠这个撑起来的。

**③ 透明/不透明标记**
用来决定哪些体素需要剔除内部面，哪些要参与透明渲染（比如水面、玻璃要单独处理）。

**④ 多级 LoD 网格**
数据是**层次化**的。一个 16³ 的 section 会不断合并降采样成 8³ → 4³ → 2³ → 1³ 的金字塔结构，每一级代表不同的精度等级。离玩家越远，用越粗的层级。

**不保留的东西：**
- 方块的具体属性（朝向、含水、含雪等）
- 方块实体数据（箱子里的东西、告示牌文字等）
- 光照信息（重新计算或用简化光照）
- 红石状态、生物信息等

所以本质上就是把一个区块从"完整 Minecraft 数据"压缩成了一份**带颜色的简化体素快照**，

如果原始区块数据量是100%的话，只保留LOD数据后大概还剩多少？

粗略估算的话：

**原版区块数据（~150-200KB/chunk）：**
- 方块状态 ID（palette + bit-packed）：~120-140KB
- 高度图、生物群系、光照、区块实体等杂项：~30-60KB

**Voxy LOD 数据（~5-15KB/chunk）：**
- 每个体素：类型(1B) + RGB颜色(3B) + 标记(1B) ≈ **5 字节**
- 多级金字塔累加：~5-15KB（取决于保留几级）

所以大概只剩 **原数据的 5%~10%** 左右 📉

压缩比这么高的原因：
1. **丢掉了大量元数据**（区块实体、光照、NBT 开销等）
2.**方块属性被扁平化**——几百种 BlockState 压缩成几十种体素类型
3. **颜色只需 3 字节**，比存储完整方块状态省太多
所以这也是为什么能存几千个区块的 LoD 数据还不爆内存——本质上就是一份**高度压缩的体素快照**，不是原版数据的副本

我问：
能否设计为两种实体种类，一种是玩家附近的全精度实体，可以用于交互，放置和破坏，一种是只保留必要信息，用于在远景的渲染。这样设计是否可行？

**完全可行，而且是体素引擎中常见的优化模式。** 让我设计具体方案。

## 两种实体的组件对比

| 组件 | 近处实体 `NearChunk` | 远处实体 `DistantChunk` |
|------|:---:|:---:|
| `ChunkComponent(Arc<ChunkData>)` | 需要（方块读写） | **去掉** |
| `Transform` | 需要 | 需要 |
| `Visibility` | 需要 | 需要 |
| `Mesh3d` | 需要 | 需要 |
| `MeshMaterial3d` | 需要 | 需要 |
| `ChunkMeshHandle` | 需要 | 需要 |
| `ChunkCoordComponent` | 需要 | 可去掉 |
| `ChunkAtlasHandle` | 需要 | 可去掉 |
| `NearChunk` 标记 | **有** | 无 |
| `DistantChunk` 标记 | 无 | **有** |

远处实体从 8+ 个组件减到 4 个，**省掉 `Arc<ChunkData>` 引用**是关键 —— 这意味着远处区块的 ChunkData 可以从内存中释放。

## 内存收益估算

| 数据 | 近处 | 远处 | 差异 |
|------|------|------|------|
| ChunkData（调色板压缩） | 保留 | **释放** | 0.5-32KB/区块 |
| 组件数 | 8-10 | 4-5 | 减半 |
| 查询命中范围 | 全量 | 仅近处 | Raycast 缩小 80%+ |

256 视距下，50,000 个区块中约 49,000 个是远处实体 → **释放 ~50-500MB ChunkData 内存**。

## 核心收益：查询隔离

```rust
// 当前：Raycast 遍历全部 50,000 个实体
fn raycast_system(chunks: Query<&ChunkComponent>) {
    for chunk in chunks.iter() { ... } // 50,000 次迭代
}

// 优化后：只查询 1,000 个近处实体
fn raycast_system(chunks: Query<&ChunkComponent, With<NearChunk>>) {
    for chunk in chunks.iter() { ... } // 1,000 次迭代
}
```

所有交互系统（方块放置、破坏、高亮、碰撞检测）都可以加 `With<NearChunk>` 过滤，查询范围缩小 50 倍。

## 迁移流程设计

当玩家移动导致区块距离变化时：

```
近处 → 远处（玩家离开）：
  1. 从 ChunkData 生成最终 Mesh（已有）
  2. 释放 ChunkData（Arc 引用计数归零）
  3. 移除 NearChunk 标记，添加 DistantChunk 标记
  4. 不再响应方块交互

远处 → 近处（玩家靠近）：
  1. 重新生成 ChunkData（通过异步 Prepare 任务）
  2. 添加 ChunkComponent
  3. 移除 DistantChunk 标记，添加 NearChunk 标记
  4. 恢复方块交互能力
```

**关键问题**：远处 → 近处迁移时，ChunkData 需要重新生成（地形噪声 + 树木），这需要 ~1-2ms/区块。可以通过**预测性预加载**（在玩家接近边界前提前提交 Prepare 任务）来消除感知延迟。

## Draw Call 问题仍然存在

这个方案解决的是 **ECS 查询开销和内存占用**，但 **不解决 Draw Call 数量**。远处实体仍然有 `Mesh3d`，仍然产生 Draw Call。

需要配合 SVO 可见性剔除（方案 B）一起使用：

```
近处实体：始终可见，始终可交互
远处实体 + SVO 可见：渲染（有 Draw Call）
远处实体 + SVO 不可见：Hidden（无 Draw Call，无 ECS 查询开销）
```

## 推荐实施路径

| 阶段 | 内容 | 收益 |
|------|------|------|
| 1 | 恢复 SVO `Visibility::Hidden` 剔除 | Draw Call 减少 60-80% |
| 2 | 添加 `NearChunk`/`DistantChunk` 标记组件 | 查询隔离，Raycast 缩小 50x |
| 3 | 远处实体移除 ChunkData，释放内存 | 内存减少 50-500MB |
| 4 | 远处 → 近处迁移的预加载 | 无缝过渡体验 |

阶段 1 和 2 可以独立实施，改动量小，收益立竿见影。阶段 3 和 4 需要仔细处理迁移边界情况。

**这个两实体方案是通往 Indirect Draw 的理想中间态** —— 先在 ECS 层面实现分层管理，后期再将远处实体替换为 GPU 驱动渲染。
